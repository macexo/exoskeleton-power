\# Contributing to exoskeleton-power



Thank you for contributing to the McMaster Exoskeleton Power Architecture subteam repository. This document outlines the development workflow, coding expectations, testing requirements, and contribution process for maintaining a reliable and organized codebase.



\## 1. Repository Organization



This repository contains firmware, testing programs, and documentation for the development of the exoskeleton's electrical power system.



\- Organize new development within the appropriate project or academic-year folder.

\- Preserve previous years' work as a reference for future development.

\- Reuse previously tested code where practical.

\- Include a project-level `README.md` for new projects, explaining their purpose, hardware configuration, build instructions, and testing procedures.

\- Do not modify the `2025-2026/` directory without prior approval from the Power subteam. Changes to historical projects should be handled separately from current development.



\## 2. Development Workflow



All new functionality should be developed on a separate Git branch and submitted through a pull request before being merged into `main`.



\### Creating a Branch



Ensure your local repository is up to date before starting new development.



```bash

git switch main

git pull

git switch -c feature/your-feature-name

```



Use descriptive branch names that reflect the work being completed.



Examples:



\- `feature/ina228-data-logger`

\- `feature/precharge-control`

\- `fix/current-sensor-calibration`

\- `docs/update-power-system-readme`



\### Committing Changes



Make commits regularly throughout development. Each commit should describe a specific change or development milestone.



```bash

git add path/to/modified/files

git commit -m "Add INA228 dual-sensor acquisition"

git push

```



For a new branch, establish its remote tracking branch using:



```bash

git push -u origin HEAD

```



Use descriptive commit messages that explain what changed. Avoid vague messages such as `update`, `changes`, or `fixed stuff`.



Unfinished work may be committed and pushed to a development branch so other team members can access it. A pull request is not required until the work is ready for review.



\## 3. STM32 Firmware Development



The Power subteam currently uses:



\- STM32CubeIDE 1.19.0

\- STM32 NUCLEO-F446RE

\- STM32F4 HAL and CMSIS libraries



New STM32 projects should retain all files required for another team member to import, compile, and flash the firmware.



\### Files to Include



\- Application source and header files in `Core/`.

\- Required HAL, CMSIS, and other project libraries.

\- STM32CubeMX configuration files (`.ioc`).

\- STM32CubeIDE project configuration files (`.project` and `.cproject`).

\- Required linker scripts and startup files.

\- Project-specific documentation and testing utilities.



\### Generated Files



Do not commit generated build outputs, including:



\- `Debug/` and `Release/` directories.

\- Compiled object files and generated executables.

\- Generated map and listing files.

\- Local IDE workspace metadata.



These files should be regenerated by STM32CubeIDE when the project is built. The repository's `.gitignore` should exclude generated build directories.



Shared debugger launch configurations may be included when they are necessary or useful for reproducing the project setup.



\### Code Organization



\- Use descriptive variable and function names.

\- Document hardware-specific configurations, including pin assignments, I²C addresses, and calibration constants.

\- Keep hardware initialization, sensor drivers, control logic, and communication functions organized.

\- Preserve STM32CubeMX-generated user-code sections when modifying generated source files.

\- Check that firmware builds successfully before submitting a pull request.



\## 4. Python Development



Python is used for data acquisition, hardware communication, testing, and data analysis.



\- Use a separate virtual environment for each project where practical.

\- Document required Python packages and installation instructions.

\- Include a `requirements.txt` file when external dependencies are required.

\- Do not commit virtual environments, Python cache files, or unnecessary generated test data.

\- Avoid hardcoding computer-specific file paths or serial port names where configurable alternatives are available.

\- Ensure scripts provide useful error messages and document their required inputs.



For Raspberry Pi projects, a virtual environment can be created using:



```bash

python3 -m venv .venv

source .venv/bin/activate

```



Install project dependencies using:



```bash

pip install -r requirements.txt

```



Include instructions for running scripts in the relevant project README.



\## 5. Hardware Testing and Validation



Changes that interact with physical hardware should be tested before being used in the integrated exoskeleton.



Testing should be performed progressively, beginning with individual components before moving to subsystem and full-system testing.



Where applicable, verify:



\- Firmware compilation and successful programming.

\- Sensor communication and initialization.

\- Voltage, current, and power measurement accuracy.

\- Sampling frequency and data integrity.

\- Communication between subsystems.

\- Fault handling and recovery behavior.

\- Emergency-stop operation and safe shutdown.

\- Power supply and grounding requirements.



Use appropriate power supplies, test loads, protection devices, and measurement equipment during electrical testing.



Do not bypass or disable safety-critical protections during integrated testing without an approved test procedure and appropriate supervision.



\### Documenting Test Results



Clearly distinguish between:



\- Functionality that has been implemented.

\- Functionality that has been tested successfully.

\- Functionality that remains untested.

\- Known limitations or issues requiring further development.



A successful software test does not necessarily establish electrical measurement accuracy or system-level safety.



Document relevant test configurations, expected results, actual results, and outstanding validation requirements.



\## 6. Pull Requests



Before creating a pull request:



\- Ensure the development branch has been pushed to the remote repository.

\- Verify that the changes are limited to the intended project or task.

\- Confirm that the project builds successfully.

\- Complete the relevant functional tests.

\- Update documentation and execution instructions.

\- Remove unintended changes, temporary debugging code, and generated build files.



A pull request should include the following sections:



\### Overview



Describe the purpose of the changes and the problem they address.



\### Changes



Summarize the important firmware, hardware configuration, software, or documentation changes.



\### Testing Completed



Describe the tests performed and their results.



\### Outstanding Validation



Identify any untested functionality, known limitations, or additional work required.



\### Review



Pull requests should be reviewed by another appropriate team member before merging into `main`.



Address review comments and make any necessary corrections on the development branch. Additional commits pushed to that branch will automatically update the open pull request.



\## 7. Documentation



Documentation should allow another team member to reproduce the development and testing environment without relying on undocumented instructions.



Project-level README files should include, where applicable:



\- Project purpose and system architecture.

\- Required hardware and software.

\- Wiring and pin assignments.

\- Sensor addresses and calibration parameters.

\- Firmware import, build, and flash instructions.

\- Python dependency installation and execution instructions.

\- Communication protocols and data formats.

\- Testing procedures and validation status.

\- Known limitations.



Update the repository's root README when adding a new project or significantly changing the repository structure.



Refer to the Embedded \& Controls repository for shared coding standards, APIs, and CAN communication conventions.



\## 8. General Expectations



\- Keep changes focused and understandable.

\- Communicate significant hardware or software changes to affected subteams.

\- Do not commit passwords, access tokens, Wi-Fi credentials, or other sensitive information.

\- Preserve working configurations and previous development milestones.

\- Avoid rewriting shared Git history without coordinating with the team.

\- Prioritize reliable, reproducible, and safe development over unnecessary complexity.
